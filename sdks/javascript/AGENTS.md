# JavaScript and TypeScript SDK instructions

Apply the root `AGENTS.md` plus these rules to `sdks/javascript/`.

## Structure and API

- Mirror the shared capability layout with `model/`, `runtime/`, `provider/`,
  and `internal/`. Keep `src/index.ts` as a documentation-backed public re-export
  facade; it must not contain implementation logic.
- In multi-member interfaces, type bodies, and classes, leave one blank line
  after the opening brace, one blank line between distinct members or member
  groups, and one blank line before the closing brace. Keep empty and one-line
  declarations compact; formatting tools remain authoritative.
- In every non-trivial function or method, leave one blank line immediately
  after `{`, blank lines between validation, normalization, construction,
  execution, and return phases, and one blank line immediately before `}`.
- Keep truly trivial one-line functions compact. For compact inline object
  literals, omit padding inside braces (`{provider, model}`); use multiline form
  when the object is not immediately readable.
- Add short `//` phase comments when names and whitespace alone do not explain a
  cohesive flow. State intent, ordering, or an invariant; do not narrate syntax
  or preserve comments that no longer add understanding.
- Add TSDoc/JSDoc to every exported type, interface, class, function, method,
  property, and error. Document rejected promises, cancellation, ownership,
  compatibility, and examples where relevant.
- Keep public contracts, runner orchestration, providers, and native loading in
  separate modules. Export only the supported API from the package entry point.
- Use strict TypeScript and ESM. Avoid `any`, broad `unknown` propagation,
  non-null assertions, and unchecked type assertions; narrow boundary input with
  explicit guards.
- Use modern TypeScript supported by the package toolchain: `satisfies`, `as
  const`, discriminated unions, exhaustive `never` checks, readonly fields,
  generics, and `unknown` plus type guards at external boundaries.
- Convert native/provider `unknown` values immediately into typed DTOs. Internal
  adapters and runners must not accept or return `Record<string, any>`, and they
  must never be exported as alternate application APIs.
- Preserve the declared npm `exports` and generated `.d.ts` surface. Treat a
  renamed export or changed optionality as a compatibility change only when root
  compatibility mode is enabled; otherwise update the complete repository.

## Async, errors, and resources

- Use promises and `async`/`await` consistently. Define cancellation with
  `AbortSignal` where supported and release native sessions in `finally`.
- Keep Node-API loading internal and produce actionable platform/architecture
  errors when a native binary cannot load.
- Keep provider transport and authentication in adapters. Never expose tokens or
  full sensitive response bodies in errors.

## Verification

- From `sdks/javascript`, run `npm ci`, `npm run check`, `npm test`, and
  `npm pack --dry-run` for package-affecting changes.
- Inspect the packed file list and declarations when exports or native artifacts
  change.
- Keep the root npm package free of `.node` files. Native artifacts ship in
  exact-version, OS/CPU-constrained optional packages generated by napi-rs.
- Never put `napi prepublish` or another registry-writing command in `prepack`,
  `prepublishOnly`, `prepare`, or any lifecycle hook reached by ordinary
  `npm pack`. Release preparation must remain an explicit command and use
  `--skip-optional-publish` plus `--no-gh-release` until the controlled publish
  job deliberately performs external writes.
- A listed napi target is supported only after CI builds its artifact and a clean
  same-platform project installs the root and platform tarballs and loads it.
